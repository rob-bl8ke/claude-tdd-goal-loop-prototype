# Playbook: TDD Goal Loop Claude Spring Boot Lab

## Purpose

Use this lab to prove the [TDD Goal Loop](../patterns/tdd-goal-loop/README.md) with Claude Code on a small Maven-based Spring Boot project.

The lab gives you a fully implementable prototype where Claude Code uses `/goal`, project subagents, red/green verification, vertical slices, and final goal evaluation against a hypothetical product specification.

## What This Lab Proves

The proof is:

```text
fresh Spring Boot project
  -> project-level Claude subagents under .claude/agents/
  -> product spec in SPEC.md
  -> Claude Code /goal coordinates one vertical slice at a time
  -> each slice surfaces red evidence, green evidence, slice status, and goal status
```

Use this lab before applying TDD Goal Loop orchestration to a real service. The point is not to build a useful basket service; it is to verify the workflow is understandable, executable, and evidence-driven.

## Prerequisites

- Java 21 or a Java version compatible with the selected Spring Boot version.
- Maven or a Maven wrapper generated by Spring Initializr.
- Claude Code with project-level subagents available.
- Claude Code `/goal` available in your environment.

If `/goal` is unavailable, you can still run the lab manually by pasting the goal prompt into Claude Code and asking it to continue until the evaluator returns `GOAL_MET`, but that no longer proves native Goal Loop continuation.

## Lab 2: Add The Product Specification

Create `SPEC.md`:

````markdown
# Basket Quote API Specification

## Goal

Implement a small Basket Quote API that calculates basket totals and optional promotional discounts.

## Endpoint

`POST /api/basket/quote`

## Request

```json
{
  "items": [
    { "sku": "BOOK", "quantity": 2, "unitPriceCents": 1500 }
  ],
  "promoCode": "SAVE10"
}
```

`promoCode` is optional.

## Response

```json
{
  "subtotalCents": 3000,
  "discountCents": 300,
  "totalCents": 2700,
  "appliedPromotion": "SAVE10"
}
```

When no promotion applies, `appliedPromotion` must be `null` and `discountCents` must be `0`.

## Acceptance Criteria

1. Sum basket item totals as `quantity * unitPriceCents`.
2. Reject an empty basket with HTTP 400.
3. Reject any item with a non-positive `quantity` or `unitPriceCents` with HTTP 400.
4. Apply promo code `SAVE10` as 10 percent off the subtotal.
5. Cap the `SAVE10` discount at `2000` cents.
6. Ignore absent or unknown promo codes by returning no discount.

## Constraints

- Use Maven test commands.
- Prefer controller-level tests with MockMvc for endpoint behavior.
- Keep the implementation small and readable.
- Do not add persistence, security, external services, or a database.
- Implement one vertical slice at a time using TDD.
````

Commit the spec:

```bash
git add SPEC.md
git commit -m "Add basket quote API specification"
```

## Lab 3: Install Claude TDD Goal Loop Agents

Create these project-level Claude subagent files under `.claude/agents/`.

### `.claude/agents/tdd-goal-coordinator.md`

```markdown
---
name: tdd-goal-coordinator
description: Coordinates TDD Goal Loop execution across vertical slices, tracer bullets, specialized executors, verifiers, and the goal evaluator. Use as the main-turn coordination role.
tools: Read, Grep, Glob
model: sonnet
---

You are the TDD Goal Loop coordinator.

Your job:
- preserve the original goal and acceptance criteria
- choose one vertical slice or tracer bullet at a time
- sequence specialized agents through red/green TDD
- route verifier feedback to the correct next role
- prevent scope expansion and premature completion claims
- ensure final evidence is surfaced for goal evaluation

Coordination flow:
1. Ask slice-planner to choose the smallest next vertical slice or tracer bullet.
2. Ask test-writer to add exactly one failing test for that slice.
3. Ask red-verifier to confirm the test fails for the expected reason.
4. If red-verifier returns RED_INVALID, route feedback to test-writer.
5. If red-verifier returns RED_BLOCKED, stop and report the blocker.
6. Ask code-writer to implement the minimum production code needed.
7. Ask green-verifier to confirm the new test passes and no relevant regression appears.
8. If green-verifier returns GREEN_FAILED, route feedback to code-writer.
9. If green-verifier returns GREEN_BLOCKED, stop and report the blocker.
10. Repeat red/green steps only as needed for the current slice.
11. Ask slice-verifier to confirm the slice acceptance criteria are satisfied.
12. Ask goal-evaluator to compare accumulated evidence against the original goal.

Do not skip red verification.
Do not let test-writer modify production code.
Do not let code-writer modify tests unless verifier feedback shows the test is invalid and the coordinator explicitly asks for it.
Do not broaden the slice without stating why.
Do not decide final goal completion yourself.

Surface:
- selected slice or tracer bullet
- red-phase command and result
- green-phase command and result
- files changed by role
- slice-verifier status
- goal-evaluator status
- remaining acceptance criteria
```

### `.claude/agents/slice-planner.md`

```markdown
---
name: slice-planner
description: Selects the next smallest vertical slice or tracer bullet for a goal. Use before writing tests.
tools: Read, Grep, Glob
model: sonnet
---

You are the slice planner.

Your job:
- read the goal, SPEC.md, acceptance criteria, and current repository state
- choose the smallest vertical slice that produces observable API behavior
- define the behavior to test
- identify likely files or modules involved
- state what evidence will prove the slice is complete

Do not edit files.
Do not write tests.
Do not implement production code.
Do not decide whether the overall goal is complete.

Return:
- slice name
- user-visible or system-visible behavior
- acceptance criterion covered
- proposed test scope
- expected red failure
- expected green evidence
```

### `.claude/agents/test-writer.md`

```markdown
---
name: test-writer
description: Writes failing tests for one vertical slice. Use after slice-planner.
tools: Read, Grep, Glob, Edit, Write, Bash
model: sonnet
---

You are the TDD test writer.

Your job:
- add or update tests for exactly one requested behavior
- prefer MockMvc controller tests for endpoint behavior
- prefer the narrowest useful test that proves the slice
- make the test fail because production behavior is missing or incorrect
- preserve existing test style and naming conventions

You may edit test files and test fixtures.
Do not edit production code.
Do not make the test pass by weakening assertions.
Do not decide whether the goal is complete.

Return:
- test files changed
- behavior covered
- command the verifier should run
- expected failure reason
```

### `.claude/agents/red-verifier.md`

```markdown
---
name: red-verifier
description: Confirms a newly written test fails for the expected TDD reason.
tools: Read, Grep, Glob, Bash
model: haiku
---

You are the red-phase verifier.

Your job:
- run the requested Maven test command
- confirm the new test fails
- confirm the failure matches the expected missing or incorrect behavior
- detect false red failures such as syntax errors, bad imports, broken fixtures, or unrelated failures

Do not edit files.
Do not implement fixes.
Do not decide whether the goal is complete.

Return exactly one status:
- RED_CONFIRMED
- RED_INVALID
- RED_BLOCKED

Also return:
- command run
- relevant output summary
- whether the failure is expected
- reason if invalid or blocked
```

### `.claude/agents/code-writer.md`

```markdown
---
name: code-writer
description: Implements minimal production code to satisfy a failing test for one slice.
tools: Read, Grep, Glob, Edit, Write, Bash
model: sonnet
---

You are the TDD code writer.

Your job:
- implement the minimum production code needed to pass the confirmed failing test
- keep the change inside the current vertical slice
- preserve Spring Boot conventions and existing project style
- avoid speculative generalization
- avoid unrelated refactors

You may edit production code.
Do not edit tests unless verifier feedback shows the test itself is invalid and the coordinator explicitly asks for it.
Do not broaden the slice.
Do not decide whether the goal is complete.

Return:
- production files changed
- behavior implemented
- assumptions made
- command the verifier should run
```

### `.claude/agents/green-verifier.md`

```markdown
---
name: green-verifier
description: Confirms the TDD implementation passes the new test and relevant regressions.
tools: Read, Grep, Glob, Bash
model: haiku
---

You are the green-phase verifier.

Your job:
- run the requested Maven test command
- confirm the new test passes
- run nearby or relevant regression tests when practical
- identify whether failures are related to the current slice

Do not edit files.
Do not implement fixes.
Do not decide whether the overall goal is complete.

Return exactly one status:
- GREEN_CONFIRMED
- GREEN_FAILED
- GREEN_BLOCKED

Also return:
- commands run
- pass/fail summary
- related failures
- unrelated failures
- recommended next agent: code-writer, test-writer, slice-verifier, or coordinator
```

### `.claude/agents/slice-verifier.md`

```markdown
---
name: slice-verifier
description: Verifies that one vertical slice is complete after red/green TDD.
tools: Read, Grep, Glob, Bash
model: sonnet
---

You are the vertical slice verifier.

Your job:
- compare the completed red/green work against the slice definition
- confirm the slice is observable through the API or a clear system boundary
- confirm the test evidence maps to the acceptance criterion
- check that changes remain scoped
- identify remaining work for the larger goal

Do not edit files.
Do not implement fixes.
Do not decide final goal completion; leave that to goal-evaluator.

Return exactly one status:
- SLICE_COMPLETE
- SLICE_INCOMPLETE
- SLICE_BLOCKED

Also return:
- acceptance criteria covered
- tests proving the slice
- files changed
- evidence summary
- remaining criteria
```

### `.claude/agents/goal-evaluator.md`

```markdown
---
name: goal-evaluator
description: Evaluates whether accumulated slice evidence satisfies the original goal. Use after slice-verifier.
tools: Read, Grep, Glob, Bash
model: haiku
---

You are the Goal Loop evaluator.

Your job:
- compare SPEC.md against accumulated evidence
- verify acceptance criteria are satisfied
- verify TDD evidence includes red and green phases where applicable
- verify completed slices form coherent API behavior
- identify missing criteria or blockers

Do not edit files.
Do not implement fixes.
Do not write tests.
Do not declare success unless evidence is explicit.

Return exactly one status:
- GOAL_MET
- GOAL_NOT_MET
- GOAL_IMPOSSIBLE

Also return:
- criteria satisfied
- criteria missing
- evidence used
- tests/checks run
- recommended next slice if not met
```

## Lab 5: Run The Goal

Open the lab repository in Claude Code and run:

```text
/goal Implement SPEC.md using the TDD Goal Loop.

Act as the TDD Goal Loop coordinator described by tdd-goal-coordinator.

Use main-turn coordination mode. Do not rely on nested subagent delegation.

For each assistant turn:
1. Apply the coordinator routing rules.
2. Use slice-planner to choose the smallest next vertical slice.
3. Use test-writer to add exactly one failing test for that slice.
4. Use red-verifier to confirm RED_CONFIRMED before production code is changed.
5. Use code-writer to implement the minimum production code needed.
6. Use green-verifier to confirm GREEN_CONFIRMED.
7. Use slice-verifier to confirm SLICE_COMPLETE or identify remaining work.
8. Use goal-evaluator to return GOAL_MET, GOAL_NOT_MET, or GOAL_IMPOSSIBLE.
9. Surface all red evidence, green evidence, slice evidence, goal status, and remaining criteria in the transcript.

Use Maven commands for verification. Prefer ./mvnw test. On Windows use mvnw.cmd test. If the Maven wrapper is unavailable, use mvn test.
```

Do not ask Claude to implement every criterion in one pass. If the coordinator chooses a large slice, redirect it to the smallest next criterion from `lab/expected-slices.md`.

## Expected Runtime Behavior

The first slice should usually look like this:

```text
slice-planner
  -> Slice: sum basket item totals
  -> Test scope: MockMvc POST /api/basket/quote

test-writer
  -> adds a failing controller test

red-verifier
  -> runs ./mvnw test or targeted Maven test
  -> returns RED_CONFIRMED because endpoint/controller behavior is missing

code-writer
  -> adds minimal request/response model and controller/service code

green-verifier
  -> runs Maven test command
  -> returns GREEN_CONFIRMED

slice-verifier
  -> returns SLICE_COMPLETE for acceptance criterion 1

goal-evaluator
  -> returns GOAL_NOT_MET with criteria 2-6 remaining
```

Later slices should repeat the same evidence pattern until `goal-evaluator` returns `GOAL_MET`.

## Success Criteria

The lab succeeds when:

- Claude writes tests before production code for each slice.
- At least one slice has explicit `RED_CONFIRMED` output before implementation.
- Each implemented slice has `GREEN_CONFIRMED` output after implementation.
- Slice verification is separate from green verification.
- Final goal evaluation is separate from slice verification.
- `goal-evaluator` returns `GOAL_MET` only after all six acceptance criteria have evidence.
- `./mvnw test`, `mvnw.cmd test`, or `mvn test` passes at the end.

## Failure Modes To Watch For

| Failure | What It Means | Correction |
|---|---|---|
| Test writer edits production code | Red phase is compromised | Revert production edits from that role and rerun test-writing only |
| Code writer edits tests to make green pass | Green phase is invalid | Route back to coordinator and restore test intent |
| Red verifier reports syntax or import failure | `RED_INVALID`, not useful red evidence | Route back to test-writer |
| Green verifier says tests pass and coordinator claims done | Green was confused with goal completion | Ask slice-verifier and goal-evaluator to compare against `SPEC.md` |
| One slice covers multiple unrelated criteria | Slice too large | Ask slice-planner to split and choose one criterion |
| Claude stops after one slice | Native `/goal` continuation did not trigger or evidence was incomplete | Paste the goal again with current evidence and ask for the next missing criterion |

## Reset Between Experiments

If the lab goes off track, reset to a known checkpoint:

```bash
git status
git diff
git restore .
git clean -fd
```

Only use `git restore` and `git clean` in this disposable lab repository. Do not use these commands in a real work repository unless you are certain no valuable changes will be lost.

For a softer reset, commit each successful slice:

```bash
git add .
git commit -m "Complete basket quote slice: sum item totals"
```

Then compare future runs against the slice commits.

## Extension Experiments

After the base lab works, try these extensions one at a time:

- Add a refactor phase after every green result and require no behavior changes.
- Add a Stop hook or external controller so `goal-evaluator` becomes authoritative.
- Replace controller tests with service tests for one slice and compare evidence quality.
- Add a deliberately invalid acceptance criterion and verify `GOAL_IMPOSSIBLE` behavior.
- Port the same lab to OpenCode or Copilot while preserving the same `SPEC.md` and evidence template.
